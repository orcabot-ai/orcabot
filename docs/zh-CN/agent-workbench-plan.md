# Herdr / T3 Code 借鉴与 Orcabot 功能规划

[English](../en/agent-workbench-plan.md) · 简体中文

研究日期：2026-11-27。状态：**在已确认的个人助手方向下提出的实施方案；不是已交付清单**。
本次为文档规划，基于仓库源码和官方资料静态核对，未重新运行产品或验证各供应商账户。

## 1. 建议定位

**Orcabot 是一个可以持续交办、跨机器执行、检查成果的个人 AI 工作台。**

保留现有“交给 Orca 一件事”的入口。首页围绕事情和决策，项目内部提供更专业的编程工作台。已确认以个人助手为主，结合感知、任务看板与明确的状态迁移。编程只是交付类型之一；Thread / Task / Run 同时支持非代码任务。

目标用户先聚焦独立开发者与技术型个人用户：同时处理几个项目，希望离开电脑后工作继续，需要回复时能找到入口，回来能检查真实产物。团队组织、独立审核身份、企业权限暂不进入本轮。

第一条目标旅程：交办“给项目补登录限流” → 选择已就绪机器和 Agent → 在隔离目录执行 → 需要信息时回复 → 检查变更与验证结果 → 提交交付 → 人工验收。个人研究、报告等任务沿用相同主线，以文件或证据引用交付。

## 4. 产品结构与交互 tips

### 首页：先告诉用户哪里需要他

推荐层级：交办输入 → 需要你处理 → 进行中 → 最近交付。注意力区始终可见，有事项时优先展示，正常工作无需持续发通知。输入前的机器、模型和目录折叠为工作上下文。

统一注意力列表涵盖：**等你回复、等待授权、等待验收、执行异常**。等待授权只在运行层确实提供授权请求时出现，不伪造通用权限控制。每条显示事情名称、具体原因、等待时长和一个主要动作，例如“回复问题”“检查交付”“恢复观察”。类别内按等待时间排序；未来加入确切截止时间后再按临期程度排序。

同一 Run 的多个问题以关联标识聚合，不能隐藏未处理动作；业务验收与运行交互保留各自身份。计数来自完整查询，不能把首页截取的几条当总量。已处理按钮重复点击不重复写入；过期请求提示重新获取；新事件到来使旧确认失效。

### 项目：对话、变更、结果是同一个现场

桌面采用项目 / Thread 导航、中央对话、按需展开的变更 / 产物区。使用现有视觉系统，不重新设计登录页。项目默认对话视图，可切列表 / 看板；不要让用户先理解多 Agent 架构才能交办。

顶部显示当前 Agent、机器与工作目录；新建编程 Thread 时展示“独立工作目录”及基线分支。Run 发出后这些执行信息作为快照保留。工具日志默认折叠，出错时展开相关记录。

结果区优先显示：改了什么、如何验证、证据或文件、仍有什么问题。程序运行完成显示“执行完成”；证据已提交显示“待验收”；仅人工审核通过后显示“已验收”。

### 手机：把一次决定做完整

先做响应式 Web 的“查看事项 → 看必要证据 → 回复 / 授权 / 验收”，保留深链接。复杂 Diff 使用单栏；键盘弹出时输入框和提交按钮仍可用；操作失败保留输入。离线只展示缓存状态与最后同步时间，写操作须连接服务后确认。原生 App、推送服务和远程中继另行排期。

### 个性化：保存工作方式

首批只提供列表、看板、专注对话三种布局及可保存筛选。后续用户说“把需要我的任务放最上面”，Agent 生成结构化配置补丁，展示预览后保存；配置有版本、校验、回退默认值。不得通过任意 JavaScript / HTML 实现初版定制，也不能允许布局隐藏必要授权和异常提示。

## 5. 分批实施与验收

按小团队、现有运行层可继续复用估算；以下为工程量级，**不是交付承诺**。先完成第一批再据实调整。

| 阶段                         | 范围与依赖                                                               | 完成条件                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| A：注意力闭环，约 3–5 工程日 | 复用现有交互和审核；统一列表、计数、动作、深链接及手机操作               | 同一事件不重复；分页不漏项；完成后正确消失；unknown 不触发新执行；320px 可完成回复和审核              |
| B：执行就绪，约 4–7 工程日   | 执行节点能力发现、框架安装 / 登录 / 目录检查；区分不支持、未登录、不可达 | 至少两种实际支持的 adapter 分别验证启动、回复、取消和恢复；报告不泄露凭证；不支持的能力明确禁用       |
| C1：隔离与 Diff，约 1–2 周   | 依赖 B；执行端 Git 操作、Thread 工作空间绑定、基线和变更快照             | 两个 Thread 并行不互改文件；脏原目录保留；无 Git 项目可用普通模式；Diff 与指定运行 / 工作区身份一致   |
| C2：Git 交付，约 1–2 周      | 依赖 C1；提交、push、草稿 PR、证据关联                                   | 操作对象明确；过期 SHA 拒绝；重复命令不重复提交 / 开 PR；远端操作结果不明先核实；冲突与认证失败能处理 |
| D：受限委派，约 1–2 周       | 依赖 B，修改代码的子任务依赖 C1；父子关联、预算、回报、取消传播          | 限深度 / 数量 / 并发；重复回报只收一次；原任务收到报告；子任务不能自行通过业务验收                    |
| E：保存视图，约 3–5 工程日   | 内置布局、筛选配置、预览和恢复默认                                       | 刷新保留；坏配置可回退；同一事项在不同视图中状态一致                                                  |

第一批演示脚本：同时准备一个待回复 Run、一个待验收任务和一个 unknown Run → 在同一注意力入口找到三者 → 回复前者、审核第二个、恢复第三个的观察 → 刷新验证记录与计数 → 手机重复打开深链接，旧请求不可再次提交。

明确后置：全量 Agent 支持、跨供应商无损原生 session 切换、插件市场、任意终端接管、自动合并发布、复杂组织权限、通用 A2UI。跨供应商接力先做“新执行 + 有来源且有界的交接摘要”，保留原 Run，不伪装成原生续接；具体上下文与授权契约另写 brief。

## 6. 工程上怎么加

沿用 `web / CLI → worker → store / workflows → runtime → OctoRuntime`。浏览器不直接运行 Git 或持有供应商凭证；普通业务任务继续使用原流程。

| 改动区域               | 建议增量（均待实施）                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `orcabot-contracts`    | Attention 的统一读取模型、Target 能力与就绪结果、ThreadWorkspace / GitChangeSnapshot；命令保留 commandId / expectedRevision |
| `orcabot-store`        | 聚合查询与稳定分页；工作空间和 Git 操作记录；后续委派关联、回报及预算。分版本迁移，保留旧数据                               |
| `apps/worker`          | 注意力聚合读接口；节点检查；Git 操作编排与身份 / 权限 / revision 校验；已提交意图再派发                                     |
| `orcabot-runtime`      | 在 SDK 实际支持范围内增加能力探测和执行端工作空间操作；先调查上游能力，缺失时明确不支持，不以普通聊天代替可靠 Git 服务      |
| `apps/web`             | 整合 Home / Attention / WorkAttention；Setup 的检查反馈；项目对话里的变更和结果区；中英、深浅色与移动端同步                 |
| `orcabot-client` / CLI | 和 Web 共用读取模型及命令，不另建一套派发语义                                                                               |

A 阶段候选 `AttentionEntry` 读取模型包含来源类型 / 标识、Thread / Task / Run 关联、actionKind、发生时间、当前 revision、深链接和必要摘要。它是事实的投影，不是第四套可变工作状态；执行状态、业务状态、连接健康分别保留。聚合分页由服务端统一排序并用稳定游标完成，不能分别截取两份列表后当完整结果。

工作空间必须在**执行机器**创建和校验：仓库根、路径归属、基线 SHA、当前 head、未提交改动均由该端确认。每个编程 Thread 可持有独立 worktree，多 Run 顺序复用；并行写入必须使用不同工作空间或阻止派发。unknown 未查清前保留工作目录，不自动清理；归档不等于删除，删除前检查未提交 / 未推送工作。

Diff 快照记录明确的比较基线和目标；审核前再次检查当前 head 与工作目录是否变化。PR / push 与业务验收分开：创建 PR 不表示已验收，验收也不自动发布。现有共享密钥仍代表同一可信操作者，不能声称具备独立用户 / Agent 授权。

## 7. 如何判断有效

首先记录可观测的本地诊断，不先接外部分析服务。指标只记录标识、状态和耗时，不记录对话与凭证内容。

- 首次成功交办：从就绪检查开始，到第一个确证执行完成的耗时及失败原因。
- 等待处理时长：从产生需要人处理的事件，到有效响应 / 审核的时间。
- 交付闭环：已提交证据中被验收 / 返工的比例；与 Run 成功率分别统计。
- 连续性：恢复观察成功率，重复派发数、重复外部操作数应为零。
- 手机闭环：能否不回桌面完成一次真实回复或审核。

实现时每阶段补对应有意义的集成与 E2E 场景，再运行仓库要求的 `pnpm check` / `pnpm e2e`。文档规划本身仅校验格式、链接与现状依据，不把现有测试的历史通过当作本次验证。

## 8. 下一步与尚需核实的细节

个人助手优先已经明确，多 Agent 编排不作为产品主界面。建议 A → B → 连续线程控制（见下文）→ 交付审核；C1 / C2 按编程任务需要引入。D 仅为可选能力，不是里程碑前置条件；E 根据实际需求安排。第一份实施 brief 应只覆盖 A，包含协议、分页、并发处理、异常和验收脚本，再按仓库 octo-spec 流程进入编码。

本方案保留现有品牌、登录页和任务验收语义；没有改变现有实现，也没有把这里的建议升级为已确认产品决策。

## 9. 上下文、执行控制与状态迁移

任务详情应把现有 WorkItem 的目标、验收标准、决策和证据，与关联 Run / Conversation 的历史放在一起阅读。保留原始来源标识和各来源分页，不再创建一套线程存储，也不悄悄合并不同执行框架的会话。返回线程时保留草稿与最近上下文；文件引用、消息引用要有来源，更早历史按需读取并限制上下文大小。

执行中需要区分“下一次发送”与“立即追加指令”。队列要持久化目标线程、顺序和版本，派发前允许编辑、删除。停止、重启或执行结果不明时，暂停后续受理，显式恢复后再继续。只有 OctoRuntime 与实际适配器具备并验证了 steer 能力，才显示立即追加入口；不能把普通后续消息包装成即时干预。现有 reply / cancel 接口不能证明支持 steer。

自定义状态表示业务阶段，不是模型随意写入的字符串。沿用版本化工作流与受校验命令：提交证据、验收通过、要求返工。模型可提出或请求允许的迁移，服务检查当前版本、执行主体权限与必要证据。已读、确认看过、批准执行动作、验收交付是四种不同操作。Routine 保留间隔限制、次数预算、原线程身份与失败暂停；日历定时另行设计。

这一阶段的验收条件：

- 重新打开任务仍能看到原始目标、决策、执行尝试和证据，成功尝试不会覆盖失败记录。
- 排队消息刷新后保留，最多派发一次；取消或 unknown 不会造成重复执行。
- 不支持的适配器不显示 steer 操作；并发编辑和过期迁移返回可恢复冲突。
- Run 完成、提交交付、验收通过保持区别；Agent 不能自己批准业务交付。
- 多端读取同一权威 worker，通过游标和新鲜度信息恢复视图，不引入对等会话复制。

## 10. 产品内的情境提示

提示只在对应条件出现，并指向真实操作，不轮播空泛的产品广告。

| 时刻           | English                                          | 简体中文                       | 操作                     |
| -------------- | ------------------------------------------------ | ------------------------------ | ------------------------ |
| 等待回答       | A quick answer will let this continue.           | 回答这个问题后，任务就能继续。 | 原地回复，保留任务上下文 |
| 观察断连       | Connection lost. This task may still be running. | 连接已断开，任务可能仍在执行。 | 恢复观察，不重新派发     |
| 提交交付       | Ready for your review.                           | 交付已提交，等待你验收。       | 打开证据与验收标准       |
| 消息排队       | This will be sent after the current run.         | 当前执行结束后发送。           | 编辑或移除排队内容       |
| 更早上下文省略 | Earlier context is available when needed.        | 需要时可以查看更早的上下文。   | 按来源读取历史           |
| Routine 暂停   | This routine paused after repeated failures.     | 连续失败后，例行任务已暂停。   | 检查尝试记录后恢复       |

失败后保留输入草稿；阅读旧消息时不强制滚到底部，只有本来就在底部时才自动跟随。手机优先展示待决定事项及其证据。未来 A2UI 使用版本化声明式组件与受校验命令；生成界面不能扩展权限，也不能在已登录页面执行任意脚本。
